# Naive Handshake Protocol

This directory contains a ProVerif model of a deliberately vulnerable public-key handshake protocol.

## Protocol

~~~text
A -> B : pkA
B -> A : aenc(sign((pkB, k), skB), pkA)
A -> B : senc(s, k)
~~~

Where:

- `pkA` is the client's public encryption key
- `skA` is the client's private encryption key
- `pkB` is the server's public signing key
- `skB` is the server's private signing key
- `k` is a fresh symmetric session key generated by the server
- `s` is the protected application secret

## Security Property

The model checks whether the attacker can derive `s`:

~~~prolog
query attacker(s).
~~~

## Verification Result

ProVerif reports:

~~~text
RESULT not attacker(s[]) is false.
~~~

This means that the attacker can derive the protected secret `s`.

## Attack Analysis

The protocol uses idealized symmetric encryption, asymmetric encryption, and digital signatures, but it is still vulnerable because the signed data is not bound to the intended client.

The attack proceeds as follows:

~~~text
Attacker I                         Server B

PKI ----------------------------->

    <----- aenc(sign((pkB, k), skB), PKI)

Attacker decrypts the response
with its own private key and learns:

- the valid server signature
- the fresh session key k


Attacker I                         Client A

                 <--------------- pkA

aenc(sign((pkB, k), skB), pkA) -->

                 <--------------- senc(s, k)

Attacker already knows k
and decrypts the ciphertext to recover s.
~~~

The attacker does not:

- break asymmetric encryption
- break symmetric encryption
- forge the server's signature

Instead, the attacker obtains a genuine server-signed session key from one protocol session and reuses that signed value in another session.

## Root Cause

The server signs:

~~~text
(pkB, k)
~~~

This proves that server B selected session key `k`.

However, it does not prove that the key was generated for client A.

The intended client's public key is missing from the signed data.

Therefore, a valid signed session key obtained for another participant can be re-encrypted under `pkA` and accepted by client A.

The protocol is missing a cryptographic binding between:

~~~text
session key k
~~~

and:

~~~text
intended client public key pkA
~~~

# Naive Handshake Protocol

このディレクトリには、意図的に脆弱なpublic-key handshake protocolをProVerifでモデル化したものが含まれています。

## プロトコル

~~~text
A -> B : pkA
B -> A : aenc(sign((pkB, k), skB), pkA)
A -> B : senc(s, k)
~~~

各値の意味:

- `pkA`: Client Aの公開暗号鍵
- `skA`: Client Aの秘密暗号鍵
- `pkB`: Server Bの公開署名鍵
- `skB`: Server Bの秘密署名鍵
- `k`: Server Bが生成するfresh symmetric session key
- `s`: 保護対象の秘密値

## セキュリティプロパティ

攻撃者が `s` を取得できるかを検証します。

~~~prolog
query attacker(s).
~~~

## 検証結果

ProVerifの結果:

~~~text
RESULT not attacker(s[]) is false.
~~~

これは、攻撃者が秘密値 `s` を取得できることを意味します。

## 攻撃の分析

このプロトコルでは、共通鍵暗号、公開鍵暗号、電子署名そのものは理想的に安全であると仮定されています。

それでも攻撃が成立する原因は、署名されたデータが本来のclientにbindingされていないことです。

攻撃の流れ:

~~~text
Attacker I                         Server B

PKI ----------------------------->

    <----- aenc(sign((pkB, k), skB), PKI)

攻撃者は自分の秘密鍵で復号し、

- Server Bによる正しい署名
- fresh session key k

を取得する。


Attacker I                         Client A

                 <--------------- pkA

aenc(sign((pkB, k), skB), pkA) -->

                 <--------------- senc(s, k)

攻撃者はすでにkを知っているため、
暗号文を復号してsを取得できる。
~~~

攻撃者は以下を行っていません。

- 公開鍵暗号の解読
- 共通鍵暗号の解読
- Server Bの署名の偽造

攻撃者は、あるセッションでServer Bから取得した正規の署名付きsession keyを、別のセッションで再利用しています。

## 根本原因

Server Bが署名している内容は、

~~~text
(pkB, k)
~~~

です。

これは、

「Server Bがsession key `k` を選択した」

ことは保証します。

しかし、

「Server BがClient Aのためにsession key `k` を選択した」

ことは保証しません。

署名対象に、本来のclient public keyが含まれていないためです。

その結果、別の参加者向けに発行された正規の署名付きsession keyを `pkA` で再暗号化し、Client Aに受け入れさせることができます。

つまり、このプロトコルでは、

~~~text
session key k
~~~

と

~~~text
intended client public key pkA
~~~

の暗号学的なbindingが欠けています。
